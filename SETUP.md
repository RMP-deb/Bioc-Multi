# Using this template

An R package skeleton for [Bioconductor](https://bioconductor.org/), following the
[Bioconductor package guidelines](https://contributions.bioconductor.org/), with optional
compiled code in C++ (via 'Rcpp') and/or Rust (via 'extendr'). Pick any combination:
R only, R + C++, R + Rust, or R + C++ + Rust.
Licensed GPL (>= 3). This file and `setup.R` are build-ignored. Delete them once you're done.

For a CRAN package, use the sibling `CRAN-Multi` template instead.

## 1. Create your package

```sh
cp -r Bioc-Multi ~/code/mynewpkg        # copy the template
cd ~/code/mynewpkg
rm -rf .git                             # drop the template's own git history
Rscript setup.R mynewpkg                # R only
Rscript setup.R mynewpkg --cpp          # R + C++
Rscript setup.R mynewpkg --rust         # R + Rust (read section 6 first)
Rscript setup.R mynewpkg --cpp --rust   # R + C++ + Rust
git init
```

Run **one** of the `setup.R` lines. It deletes the files for the languages you didn't
pick, replaces `pkgname` everywhere, regenerates the Rcpp glue (if you kept C++) and
deletes itself. With `--rust` the name may only contain letters and numbers (no `.`),
because it is also the Rust crate name.

Bioconductor requires a name not already used on CRAN or Bioconductor:
`BiocManager::available("^mynewpkg$")` and `pak::pkg_name_check("mynewpkg")`.

## 2. Fill in placeholders

| File | What to change |
|---|---|
| `DESCRIPTION` | `Title`; `Description` (**at least 3 sentences**); `Authors@R` (real maintainer email; add `comment = c(ORCID = "0000-...")` if you have one, and a `fnd` person for funders); `URL`/`BugReports` (`USERNAME`); `biocViews` (see below); `Depends: R (>= ...)` |
| `README.Rmd` | Goal, example. Render it with `devtools::build_readme()` |
| `vignettes/<name>.Rmd` | Author, abstract, a real worked example on small data. **Required by Bioconductor.** |
| `NEWS.md` | Keep one entry per version |
| `_pkgdown.yml` | `USERNAME` (or delete it if you don't use pkgdown) |
| `R/hello.R` | Example R code: replace with your own (plus its test) |
| `src/sumSquaresCpp.cpp` | Example C++ code (plus its test) |
| `src/rust/src/lib.rs` | Example Rust code (plus its test) |
| `src/rust/Cargo.toml` | Crate `version`, `rust-version` (MSRV); keep in sync with `rustc >= ...` in DESCRIPTION's `SystemRequirements` |
| `inst/scripts/make-data.R` | How each dataset was made. Delete if you ship no data |

**biocViews**: replace the placeholder `Software, Infrastructure` with terms from the
[biocViews vocabulary](https://bioconductor.org/packages/devel/BiocViews.html#___Software)
describing what the package does, e.g. `biocViews: Software, GeneExpression,
RNASeq, Transcriptomics`. `BiocCheck` rejects terms that aren't in the list, and
`Software` alone is an error.

**R version**: `Depends: R (>= ...)` should match the R version of the current
Bioconductor devel release; `BiocCheck` tells you if it's out of date.

**Version**: new submissions start at `0.99.0`. Bump the last number (`0.99.1`,
`0.99.2`, ...) for every change you push during review: the Bioconductor builder only
rebuilds when the version changes. When the package is first released, Bioconductor
sets it to `1.0.0`. After that, versions are `x.y.z` with even `y` in release and odd
`y` in devel. Don't use CRAN-style `.9000` development versions.

## 3. Layout

Lines marked **[C++]** or **[Rust]** only exist if you picked that language.

```
DESCRIPTION            package metadata (incl. biocViews)
NAMESPACE              generated by roxygen2: don't edit by hand
LICENSE.md             full GPL-3 text (build-ignored; R knows GPL-3)
NEWS.md                changelog (shown on the Bioconductor landing page)
README.Rmd / .md       GitHub landing page
R/                     R code
  pkgname-package.R    package docs (+ @useDynLib / @importFrom Rcpp with C++)
  RcppExports.R        [C++]  generated R wrappers for C++: don't edit by hand
  extendr-wrappers.R   [Rust] generated R wrappers for Rust: don't edit by hand
src/                   compiled code (absent for R-only packages)
  *.cpp                [C++]  your C++ source
  RcppExports.cpp      [C++]  generated glue + the package's R_init function: don't edit
  init-rust.cpp        [C++ + Rust] hooks extendr's panic handler into Rcpp's R_init
  entrypoint.c         [Rust only] C glue that registers the Rust library with R
  Makevars.in          [Rust] build template (configure turns it into Makevars)
  Makevars.win.in      [Rust] same, for Windows
  pkgname-win.def      [Rust] Windows export definitions
  rust/                [Rust]
    Cargo.toml         Rust crate manifest (dependencies go here)
    src/lib.rs         your Rust code
    document.rs        helper binary that generates R/extendr-wrappers.R
configure(.win)        [Rust] run at install: checks cargo/rustc, writes src/Makevars
cleanup(.win)          [Rust] removes generated Makevars
tools/                 [Rust] config.R and msrv.R, used by configure
.vscode/               [Rust] rust-analyzer settings (build-ignored)
man/                   generated .Rd docs: don't edit by hand
tests/testthat/        unit tests (required by Bioconductor)
vignettes/             BiocStyle vignette (required by Bioconductor)
inst/scripts/          scripts documenting how data in data/ or inst/extdata/ was made
inst/extdata/          raw example files (create when needed; read with system.file())
.github/workflows/     R CMD check + BiocCheck on Bioconductor devel; macOS/Windows checks
```

## 4. Bioconductor conventions

`BiocCheck` enforces some of these; reviewers enforce the rest.

**Style** ([Bioconductor style guide](https://contributions.bioconductor.org/r-code.html)):

* 4-space indentation, no tabs, lines of at most 80 characters.
* camelCase function names (`sumSquaresCpp()`, not `sum_squares_cpp()`). In Rust keep
  snake_case and set the R name with `#[extendr(r_name = "camelCase")]`.
* `seq_len(n)` / `seq_along(x)` instead of `1:n`; `vapply()` instead of `sapply()`;
  `TRUE`/`FALSE`, never `T`/`F`; no `paste()` inside `stop()`/`warning()`/`message()`
  (they already concatenate); no `print()`/`cat()` for messages (use `message()`).
* No `install.packages()`, `browser()`, `<<-` or `set.seed()` inside package functions.

**Design**:

* Reuse Bioconductor classes for inputs and outputs (`SummarizedExperiment`,
  `SingleCellExperiment`, `GRanges`, `DNAStringSet`, ...) instead of inventing your own.
  This is the most common reason reviewers ask for changes.
* A fresh copy of this template passes `BiocCheck` with 0 errors, 0 warnings and a few
  notes: ORCID and `fnd` (funder) suggestions, two roxygen-generated lines in the
  package man page, and "No Bioconductor dependencies detected". That last one becomes
  a **warning** once you replace the `Infrastructure` biocView, unless you import a
  Bioconductor package (e.g. `usethis::use_package("SummarizedExperiment")`). A package
  with no reason to depend on any Bioconductor package may be told to go to CRAN.
* Prefer `Imports:` over `Depends:`. Only put a package in `Depends:` if users need it
  attached to use yours.
* Large data belongs in an ExperimentHub/AnnotationHub package, not in the software
  package. The package tarball must stay under 5 MB.
* Every exported function needs a man page with `@returns` and a runnable example.
  Use `\donttest{}` rarely and `\dontrun{}` almost never.
* `R CMD check` must finish in under 10 minutes on the builders.

**Vignette**: at least one, with evaluated code that shows a realistic workflow.
Install instructions must be in a chunk with `eval = FALSE`, and the vignette should end
with `sessionInfo()`. Keep the `BiocStyle::html_document` output.

## 5. Writing C++

* Put `.cpp` files in `src/`. Tag each function you want callable from R with
  `// [[Rcpp::export]]` on the line above it.
* Document with `//'` roxygen comments in the `.cpp` file. Add `//' @export` to make
  the function public; leave it off for internal helpers you wrap in R code.
* Run `devtools::document()` after changing signatures: it runs
  `Rcpp::compileAttributes()` and regenerates `RcppExports.*`, `NAMESPACE` and `man/`.
* `devtools::load_all()` recompiles changed files.
* Compiler flags go in `src/Makevars` (and `src/Makevars.win`), e.g.
  `PKG_CXXFLAGS = -O2`. Recent R defaults to C++17. To require a different standard,
  set `CXX_STD = CXX20` in Makevars and add `SystemRequirements: C++20` to DESCRIPTION.
  (If you also use Rust, put these lines in `src/Makevars.in` / `src/Makevars.win.in`
  instead: `src/Makevars` is generated by `configure` and git-ignored.)
* Bioconductor has C++ libraries you can link to, e.g. 'Rhtslib' (htslib) or
  'beachmat'. Add them to `LinkingTo:` (and `Imports:` if you call their R functions).
* Rules: code must compile warning-free with gcc and clang on Linux, macOS and Windows,
  no `std::cout`/`printf` (use `Rcpp::Rcout`/`Rprintf`), no `exit()`/`abort()`,
  check for interrupts in long loops (`Rcpp::checkUserInterrupt()`), and never ship
  compiled `.o`/`.so` files.

## 6. Writing Rust (check with Bioconductor first)

**Rust support on the Bioconductor build machines is not settled.** As of 2025-2026,
cargo was installed on the Linux builders but not on all macOS/Windows builders, and
Bioconductor hadn't formally adopted `rustc` as a supported system requirement. Before
you build a package around Rust, ask on the
[bioc-devel mailing list](https://stat.ethz.ch/mailman/listinfo/bioc-devel) whether
it will build on all platforms. C++ is the safe choice.

* Write functions in `src/rust/src/lib.rs` (or other modules), mark them with
  `#[extendr]` (or `#[extendr(r_name = "myName")]` for a camelCase R name) and list
  them in the `extendr_module!` block.
* Document with `///` comments using roxygen tags (`@param`, `@returns`, `@export`,
  `@examples`).
* Run `devtools::document()` after changing Rust code. It compiles the crate and
  regenerates `R/extendr-wrappers.R`, `NAMESPACE` and `man/`.
* Add crates with `rextendr::use_crate("serde")` or by editing `Cargo.toml`.
  Commit `src/rust/Cargo.lock`.
* `rextendr::rust_sitrep()` diagnoses toolchain problems.
* Set `NOT_CRAN=true` for faster local dev builds that don't use the vendor tarball.
  `DEBUG=true` gives a debug build.
* For offline builds, `rextendr::vendor_crates()` writes `src/rust/vendor.tar.xz`, and
  `rextendr::write_license_note()` writes `LICENSE.note` crediting the crate authors.
  Add the crate authors to `Authors@R` (e.g. `person("authors of the dependency Rust
  crates", role = "ctb", comment = "see LICENSE.note")`). Watch the 5 MB size limit.

## 7. Using C++ and Rust together

A package can only have one `R_init_<pkg>()` function, and both Rcpp and extendr want to
generate one. When both are present, Rcpp's wins: `Rcpp::compileAttributes()` scans
`R/extendr-wrappers.R` for `.Call(wrap__...)` and registers the Rust routines alongside
the C++ ones in `src/RcppExports.cpp`. `src/init-rust.cpp` adds extendr's panic hook to
that init function, so `entrypoint.c` isn't needed (and `setup.R` removes it).

One consequence: Rcpp only sees a new Rust function after the wrappers are regenerated.
**When you add, remove or rename a Rust function, run:**

```r
devtools::document()        # compiles Rust, rewrites R/extendr-wrappers.R
Rcpp::compileAttributes()   # registers the new set of wrap__* routines
devtools::document()        # recompiles with the updated registration
```

Signs you forgot: `object 'wrap__foo' not found` (added) or
`undefined symbol: wrap__foo` (removed). Changes inside existing Rust functions only
need the usual single `devtools::document()` / `load_all()`.

Keep exported names distinct across languages (e.g. not `foo()` in both C++ and Rust).

## 8. Daily workflow

```r
devtools::load_all()     # Ctrl+Shift+L
devtools::document()     # Ctrl+Shift+D: regenerate NAMESPACE, man/ and compiled-code glue
devtools::test()         # Ctrl+Shift+T
devtools::check()        # Ctrl+Shift+E: full R CMD check
BiocCheck::BiocCheck()   # Bioconductor-specific checks (run on the package folder)
usethis::use_r("foo")    # new R/foo.R
usethis::use_test("foo") # new tests/testthat/test-foo.R
usethis::use_package("SummarizedExperiment")  # add to Imports
```

Develop against **Bioconductor devel**, which is what new submissions are built with.
It may need a newer R than your current one; see
<https://bioconductor.org/developers/how-to/useDevel/>. You can use the
`bioconductor/bioconductor_docker:devel` image locally too.

## 9. Submitting to Bioconductor

The full process is at <https://contributions.bioconductor.org/submission-overview.html>.
The core steps:

1. The maintainer must be registered on <https://support.bioconductor.org> (with the
   package name in "Watched Tags") and subscribed to the
   [bioc-devel mailing list](https://stat.ethz.ch/mailman/listinfo/bioc-devel).
2. Version `0.99.0`, a public GitHub repo, and the default branch named `devel`
   (Bioconductor's git server uses `devel`).
3. `devtools::check()`: 0 errors, 0 warnings, ideally 0 notes.
4. `BiocCheck::BiocCheck()`: 0 errors. Fix the warnings, and the notes where you can.
5. Open an issue at <https://github.com/Bioconductor/Contributions> with the repo link,
   and add the SSH key / webhook it asks for.
6. During review, bump the version (`0.99.1`, ...) with every push so the builder
   rebuilds the package. Answer reviewer comments in the issue.
7. After acceptance, push to `git.bioconductor.org` (and keep GitHub in sync). Bug fixes
   go to both the release and devel branches.
